  Short answer

  Zernio can give Clinch its own phone number — but only for SMS / MMS / 
  WhatsApp / voice. It does not do iMessage. I confirmed this three ways:
  Zernio's own docs list the phone channels as "SMS, MMS, WhatsApp, and voice
  calls" (no iMessage/RCS), the send endpoint is POST /api/v1/sms/messages, and
  the Chat SDK adapter's platform list (Instagram, Facebook, X, Telegram,
  WhatsApp, Bluesky, Reddit) has no iMessage entry.

  So whether Zernio solves your problem depends entirely on one thing: do you 
  actually need iMessage (blue bubbles), or do you just need a real second 
  number the user can text?

  Why "text yourself" happens today

  ★ Insight ─────────────────────────────────────
  Both the native Clinch feature and the installed plugin work the same way:
  they drive the Mac's local Messages.app via osascript and read 
  ~/Library/Messages/chat.db read-only to catch replies. Crucially, they send
  from the Apple ID already signed into that Mac — there's no separate identity.
  So the only number Clinch can be is you, which forces a self-conversation
  (one logical message becomes a sent row + a received row with different
  GUIDs). Most of the code's complexity — the GUID echo-suppression, the
  MirroredMessageFingerprint twin-row coalescing, the 15s echo window — exists
  purely to survive texting yourself.
  ─────────────────────────────────────────────────

  That's the constraint you're trying to break. A dedicated number breaks it —
  the question is which technology backs that number.

  The real fork in the road

  Path A — Accept SMS (green bubbles). Zernio works here.
  Provision a Zernio number, Clinch sends completions via POST 
  /api/v1/sms/messages, inbound replies arrive on a message.received webhook.
  This cleanly deletes the whole self-chat problem: the user texts a genuine
  second number, no Full Disk Access, no chat.db polling, no osascript, no GUID
  dedup. Architecturally it's dramatically simpler than what's on the feature
  branches.

  Path B — Keep iMessage (blue bubbles). Zernio can't help.
  There is no clean API for a new, independent iMessage identity — Apple doesn't
  sell one. The "iMessage API" vendors that showed up in the search
  (LoopMessage, Sendblue, Blooio) get blue bubbles by running a real Apple ID on
  a dedicated Mac/device and relaying through it — i.e. the same
  osascript+chat.db trick Clinch already does, just hosted. To get a separate
  iMessage number you'd need a separate Apple ID + a dedicated device/relay,
  typically a paid monthly SaaS, and it stays fragile and ToS-gray.

  The trade-off worth flagging before you pick

  ★ Insight ─────────────────────────────────────
  The feature was deliberately built local-only and private: its config is a
  SecureSetting with sync_to_cloud() = SyncToCloud::Never, is_private() = true,
  and routing state is persisted with owner-only 0o600 permissions. Zernio
  inverts that — your agent output (and whatever context is in those completion
  messages) would now transit a third-party cloud API. That's not a blocker, but
  it's a genuine philosophy change from "nothing leaves the Mac" to "messages
  relay through a vendor," and it's the kind of thing worth deciding on purpose
  rather than by accident.
  ─────────────────────────────────────────────────

  My recommendation

  If iMessage-specifically was never the point — you just wanted the assistant
  to reach the user's phone without the self-texting hack — Path A with a cloud 
  SMS provider is the right move, and Zernio is a plausible pick (though I'd
  weigh it against Twilio, which is the incumbent for exactly this: mature
  webhooks, number provisioning, and it's not primarily a social-media tool with
  SMS bolted on). If blue-bubble iMessage is a hard product requirement, Zernio
  is simply the wrong tool and you're looking at a dedicated-Apple-ID relay
  instead.

  So before any building: is the requirement "iMessage," or is it "a dedicated 
  number so the user stops texting themselves"? That answer decides everything
  downstream. If it's the latter, I'm happy to brainstorm the Zernio-vs-Twilio
  integration against the existing coordinator architecture.

⏺ Design — Checkpoint 1 of 2: core architecture

  Overview & scope

  Clinch gets its own Telegram bot that the user runs from their own @BotFather
  token. In a private Telegram supergroup (Topics enabled, bot as admin), Clinch
  maintains one named forum topic per agent session, titled project · session
  (e.g. clinch-terminal · fix-auth). Agents post updates into their topic; the
  user replies inside a topic and the reply is injected straight back into that
  exact live session. Topics close when a session ends and reopen if it resumes.
  Fully two-way, fully backendless — the Mac talks directly to
  api.telegram.org, no Clinch server, no third party.

  This is a fresh build on main, not a revival of the removed iMessage code. It
  borrows proven concepts from the old app/src/imessage/domain.rs (session
  routing, dedup, FIFO queues, long-message splitting) but drops everything
  platform-specific to Apple: no Swift helper, no osascript, no chat.db, no Full
  Disk Access, no Apple Events entitlement. The transport is just HTTPS.

  Architecture & components

  New module app/src/telegram/, mirroring the old module's clean split of pure 
  domain vs side-effecting transport:

  File: mod.rs
  Responsibility: Module root, exports coordinator
  Reuses / replaces: new
  ────────────────────────────────────────
  File: coordinator.rs
  Responsibility: TelegramCoordinator singleton: owns config, the outbound
  queue,
  the inbound long-poll task, and the session↔topic map. Subscribes to agent
  StatusChanged events.
  Reuses / replaces: adapts old imessage/coordinator.rs orchestration
  ────────────────────────────────────────
  File: domain.rs
  Responsibility: Pure, side-effect-free: topic-title formatting, session↔topic
  routing, reply classification, dedup, FIFO queue, message splitting. Fully
  unit-testable.
  Reuses / replaces: adapts old imessage/domain.rs
  ────────────────────────────────────────
  File: client.rs
  Responsibility: Thin async Telegram Bot API client:
  create/edit/close/reopen/deleteForumTopic, sendMessage(message_thread_id),
  getUpdates(offset). All HTTPS. Behind a TelegramTransport trait so tests
  inject a fake and no test hits the network.
  Reuses / replaces: replaces old bridge.rs + Swift helper
  ────────────────────────────────────────
  File: store.rs
  Responsibility: Atomic, owner-only (0o600) JSON persistence of the
  session↔topic map, update offset, and group id.
  Reuses / replaces: reuses old imessage/store.rs pattern verbatim
  ────────────────────────────────────────
  File: tests.rs
  Responsibility: Domain + coordinator tests against the fake transport.
  Reuses / replaces: adapts old imessage/tests.rs

  Settings: new TelegramConfiguration + TelegramConfigurationSetting in
  app/src/settings/clinch.rs, copying the old IMessageConfiguration's security
  posture exactly — SecureSetting, sync_to_cloud() = Never, is_private() = true,
  Mac-local. Fields: bot_token (secret), group_chat_id, allowed_user_ids,
  enabled.

  ★ Insight ─────────────────────────────────────
  The old feature needed a separate Swift process because Apple gives no
  send/receive API — you had to drive the GUI app and scrape SQLite. Telegram is
  an API, so the entire bridge.rs subprocess + 688-line Swift helper collapses
  into one in-process client.rs making HTTPS calls. That's why hiding the
  transport behind a TelegramTransport trait is worth it: it's the one seam
  where the network lives, so it's the one thing tests must fake.
  ─────────────────────────────────────────────────

  Data flow

  Outbound (agent → you):
  Agent session turn completes / needs input
        │  StatusChanged  (existing event)
        ▼
  TelegramCoordinator
    • look up session → topic id in the map
    • none? client.createForumTopic("project · session") → store id
    • topic closed (session was resumed)? client.reopenForumTopic
    • split body to ≤4096 chars → FIFO OutboundJob(s)
        ▼
  client.sendMessage(chat_id, text, message_thread_id = topic)

  Inbound (you → agent):
  Background task: client.getUpdates(offset) long-poll  ── loops while app runs
        ▼  Message with message_thread_id + is_topic_message
  TelegramCoordinator
    • sender in allowed_user_ids?  (else drop)
    • message_thread_id → session key   (the topic IS the routing key — no route
  codes)
    • session live? → TerminalView::submit_external_reply into that exact pane
    • session gone? → reply in-topic: "session ended" (optionally offer resume)
    • advance stored offset only after handling

  No route codes, no menus, no calibration handshake for routing — the topic a
  message sits in is the address. That's the whole payoff of the topic model.

⏺ Design — Checkpoint 2 of 2: setup, lifecycle, safety, errors, testing

  Setup / onboarding UX

  A one-time flow in Clinch settings (new "Telegram" section), designed so the
  fiddly Telegram steps are guided, not guessed:

  1. Create bot — link out to @BotFather; user pastes the token into a secret
  field. Clinch calls getMe to validate and show the bot's @handle.
  2. Create the group — Clinch shows exact steps: new group → enable Topics
  (making it a supergroup) → add the bot → promote to admin with Manage Topics.
  3. Auto-discover the group id (handshake) — instead of asking the user to find
  a chat id, Clinch long-polls getUpdates and waits for the bot to be added.
  When it sees a my_chat_member / group update, it captures group_chat_id and
  posts a confirmation topic "✅ Clinch connected". Clinch then verifies
  is_forum: true and its own admin can_manage_topics right, surfacing a fix-it
  message if either is missing.
  4. Auto-capture allowed user — the first person to reply in that confirmation
  topic is offered as the allowed user id (one tap to approve). This is the
  Telegram-native replacement for the old calibration code.

  ★ Insight ─────────────────────────────────────
  This reuses the shape of the old feature's calibration handshake (prove
  control of the channel before trusting it) but gets it for free from
  Telegram's update stream — no one-time-code round trip. The bot literally
  cannot be added to your group by anyone but you, so "who added me" is already
  a trust signal.
  ─────────────────────────────────────────────────

  Topic naming, lifecycle & dedup

  - Title: project · session, from the existing project-tab name + the session
  label (the same source the tab bar uses). Renamed via editForumTopic if the
  tab is renamed.
  - Collision / uniqueness: the session↔topic map is keyed by the durable
  session key (CLIAgentSessionKey), never by title — two sessions with identical
  titles still get distinct topics; a duplicate title just gets a  (2) suffix
  for human readability.
  - Lifecycle state machine (persisted in store.rs): Active → (session ends) → 
  closeForumTopic → Closed → (session resumes) → reopenForumTopic → Active.
  History always preserved. deleteForumTopic is never called automatically —
  only via an explicit user "forget this session" action.
  - Orphans: on startup Clinch reconciles the map against live sessions; a
  mapped topic whose session no longer exists is closed (not deleted).

  Access control & privacy

  - Scope: Clinch only ever posts to / reads from the one configured
  group_chat_id. Updates from any other chat are ignored.
  - Allowlist: inbound replies are honored only from allowed_user_ids;
  everything else is dropped (mirrors the plugin's allowFrom model). Group is
  private, so this is defense-in-depth.
  - Secrets: bot_token lives in the same SecureSetting / SyncToCloud::Never /
  owner-only-file regime as the old iMessage config — never cloud-synced, 0o600
  on disk.
  - Privacy disclosure (documented, not hidden): unlike the removed local-only
  iMessage feature, message content now transits Telegram's cloud. This is
  inherent to any remote-notification channel and you've chosen it deliberately;
  the design just states it plainly in the settings UI and spec so it's a
  conscious trade, and keeps the feature off by default.

  Best practices for an all-day coding terminal (that hosts other agents)

  1. Legibility ≠ maximum contrast. Pure white on pure black (#FFF on #000) is
  the classic beginner move and it's fatiguing — the high luminance gap causes
  halation (text "glows" and smears) over long sessions. Best practice: a soft 
  off-white foreground (~#C7D3E2) on a dark-but-not-black background (~#0E1622).
  Aim for a contrast ratio in the comfortable 11:1–14:1 band, not the maximal
  21:1. Same logic inverts for light mode: warm/cool paper, never #FFFFFF.

  2. The 16 ANSI colors are 90% of what you actually stare at. Syntax
  highlighting, ls, git, diffs, and both agents' UIs all render through the
  terminal's 16-color palette. If those are neon, everything is exhausting; if
  they're muddy, code is unreadable. The target is muted jewel tones with strong
  hue separation — calm enough for 8 hours, distinct enough that red≠magenta
  and blue≠cyan at a glance.

  3. Tune "bright black" deliberately — it's the agent secondary-text color.
  Claude Code and Codex lean heavily on ANSI bright-black/gray for dim text, box
  borders, and "thinking" lines. If bright-black collapses into your
  background, their UIs lose structure. Pin it clearly above the background
  (~#6B7C96 on navy). This one color does a lot of quiet work.

  4. Keep the brand lime OUT of the terminal grid. This is the big one for agent
  compatibility. Claude Code's accent is warm (tan/orange); Codex has its own.
  If your lime is also a terminal color, it collides with whatever the agents
  paint. So: lime lives only in Clinch's native chrome (active tab, cursor,
  focus ring, footer primary) — never as an ANSI color. In the palette,
  "success/added" green is a separate, calmer green. Lime stays special because
  it appears in exactly one visual language.

  5. Selection & search must be translucent. Agents render colored text you'll
  want to select over. A solid selection block erases their color; a
  semi-transparent tint (~28% alpha) preserves it. Give search-match a different
  hue from diff-add so "found it" never reads as "added line."

  6. Spend boldness in one place. Per good design discipline: one signature
  element, everything else quiet. My proposed signature is a single lime "spine"
  marking the focused tab/pane + a lime block cursor — and lime appears
  essentially nowhere else. Restraint is what keeps it from looking like the
  generic "acid-green-on-black" theme every AI reaches for.

⏺ Verified — and the results actually strengthen the plan:

  - JetBrains Mono — confirmed SIL OFL 1.1 (free to bundle/redistribute in
  Clinch) and it explicitly ships Box Drawing (U+2500–257F) + Block Elements 
  (U+2580–259F). Important nuance I found: its box-drawing glyphs render
  seamlessly only at generous line-height (there's a known issue about them not
  being full-height at tight spacing) — which is exactly why my proposed ~1.6 
  line-height default matters. So the font choice and the line-height default
  reinforce each other. (JetBrains Mono (https://www.jetbrains.com/lp/mono/),
  supported symbols
  (https://github.com/JetBrains/JetBrainsMono/wiki/List-of-supported-symbols),
  box-drawing height issue
  (https://github.com/JetBrains/JetBrainsMono/issues/165))
  - Monaspace Neon (the alternative) — also OFL 1.1, but its base box-drawing
  coverage is less clearly documented than JetBrains'. So JetBrains Mono is the
  safer default; Monaspace stays a noted alternative. (Monaspace
  (https://github.com/githubnext/monaspace))

  raw lime should be a brand-spark constant used for exactly two things — the

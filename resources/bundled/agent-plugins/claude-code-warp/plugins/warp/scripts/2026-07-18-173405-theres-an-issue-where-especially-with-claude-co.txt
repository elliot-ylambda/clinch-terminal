  How Clinch decides an agent is "working"

  The in-progress indicator you see (the project-tab spinner, hover badge, and
  footer status) is not based on watching PTY output or an idle timer. It's a
  small state machine fed entirely by structured OSC-777 events that the bundled
  Claude Code plugin emits from hooks:

  app/src/terminal/cli_agent_sessions/mod.rs:337 — apply_event() is the whole
  thing. The status enum has three values:

  pub enum CLIAgentSessionStatus { InProgress, Success, Blocked { message } }

  And the "is it working" boolean the UI reads (mod.rs:322):

  pub fn is_actively_working(&self) -> bool {
      self.has_observed_turn_activity && matches!(self.status, InProgress)
  }

  The events come from six wired Claude hooks (hooks.json): UserPromptSubmit → 
  prompt_submit, PostToolUse → tool_complete, Stop → stop,
  Notification(idle_prompt) → idle_prompt, PermissionRequest, SessionStart.

  ★ Insight ─────────────────────────────────────
  - InProgress is "sticky." Only prompt_submit (and recovery from a
  Blocked/interrupted state) enters it; only Stop or idle_prompt leaves it (→
  Success). Nothing is time-based.
  - There is no "a subagent is running" signal. PreToolUse and SubagentStop are
  deliberately not wired. Clinch only ever learns a tool finished
  (tool_complete), never that one started.
  - tool_complete can't revive a stale Success (mod.rs:368-378): it only re-arms
  InProgress from Blocked or a user-interrupt guess. So once the pane flips to
  "done," subagent tool activity can't turn it back on.
  ─────────────────────────────────────────────────

  Where the subagent case breaks

  When the main agent dispatches a subagent (the Task tool), the main turn is
  genuinely still running — but Clinch has no positive signal to keep the pane 
  lit, and no way to recover if it ever flips to Success. The gap is real; the
  exact trigger of the flip is what determines the cleanest fix, and there are
  two candidates:

  1. A premature Stop/idle_prompt fires while the subagent is mid-flight (e.g. a
  subagent completion surfacing as a top-level Stop), latching the pane to
  Success — and then subagent tool_complete events can't revive it.
  2. No premature signal fires, the pane does stay InProgress, and what you're
  noticing is a different indicator or a gap right at dispatch.

  These lead to different fixes, so I don't want to build on a guess. One
  question pins it — and I can also just verify it empirically by capturing the
  real OSC event stream during a subagent dispatch, which I'd recommend either
  way before writing code.

  What's actually happening

  Look at the state: the main agent has dispatched a background agent (○ 
  general-purpose  Review Tasks 1-2 + rebase, ← 1 agent, "Waiting for 1
  background agent to finish") and then yielded control back to the prompt (the
  › cursor is live). The left tab shows a green checkmark — Clinch's Success
  state.

  That's the bug. Here's the exact sequence against the state machine I mapped:

  1. You submit → UserPromptSubmit → prompt_submit → InProgress ✓ (spinner)
  2. Main agent dispatches a background subagent (Task with background) → the
  tool call returns a handle immediately
  3. Main agent's turn ends and hands the prompt back → Stop → Success ← green
  check appears here
  4. …background agent keeps running for minutes… no events Clinch understands
  5. Background agent finishes → SubagentStop (which Clinch doesn't listen for)
  → main agent auto-resumes

  ★ Insight ─────────────────────────────────────
  - Background agents decouple the main turn from the main session's work. A
  foreground subagent keeps the parent turn open (so Stop never fires early, and
  the pane stays lit on its own). A background subagent lets the parent turn
  Stop while work continues — and Stop is exactly the signal Clinch treats as
  "done."
  - Clinch has no "N agents still running" signal. Claude Code knows it (← 1 
  agent in its own footer), but that count is never emitted to the plugin's
  hooks, so Clinch can't reflect it.
  - So the fix isn't "keep InProgress sticky" — it's "teach Clinch that 
  background agents are outstanding, and don't report Success until they're all 
  done."
  ─────────────────────────────────────────────────

  Approaches

  A — Outstanding-subagent tracker (recommended). Wire two hooks the plugin
  currently ignores: PreToolUse(Task) → "subagent started" and SubagentStop →
  "subagent finished." Track the set of outstanding subagents on the
  CLIAgentSession. While any are outstanding, a Stop/idle_prompt keeps the
  session working instead of flipping to Success. This models reality and
  handles foreground and background subagents uniformly.

  B — Revive "working" on any tool activity. Make tool_complete (and a new
  tool_start) pull the session out of a stale Success. This is a good safety net
  for recovery, but alone it does not fix your screenshot — during the "Waiting
  for 1 background agent" window there's no tool activity at all, so the pane
  would still show done for the whole wait. I'd fold this in as a complement to
  A, not the primary fix.

  C — Screen-scrape Claude's "N agents" footer. Rejected — fragile, and we
  already have a structured hook channel.

  I'm recommending A (+ B as a safety net). The one thing I want to nail down
  before writing the spec is the actual hook sequence for background agents on
  your Claude Code (v2.1.214) — specifically: does PreToolUse(Task) fire at
  background dispatch, does SubagentStop reliably fire on completion, and do
  their payloads carry a subagent id I can use to add/remove by identity
  (leak-proof) rather than a raw counter.

  I'd like to verify that empirically first — instrument the hooks to log every

  on observed behavior, not my assumptions about the hook API. Want me to run
  that capture now, or would you rather I go straight to writing the design spec
  on the strength of the reasoning above?
